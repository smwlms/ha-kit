# Phase 4: module split and contracts

Status: **contracts fixed; every phase-4 module built** (wave 1: `tariff-be`, `energy-plan`, `charger-zappi`, `heat-pump-vaillant`, `home-screen`; wave 2: `ev-charging`, `hot-water`, `climate`, `appliances-home-connect`, `energy`; wave 3: `results`), all `built, not tested on HA`. Their clarifications are merged below: per module in section 4 the **Notes from wave 1** (what wave 1 expected) and **Built** (what the builder added to the contract: extra entities, attributes and states; no fixed id, state or event of this file was changed). Their `house.yaml` fields are in `house.example.yaml`. This file is the single source for anyone who builds a second brand, region or a module that reads these: energy, tariff, EV charging, heat pump, hot water, climate, appliances, results and the home screen.

Sources are the maintainer's own live setup (outside this repository): the export of the live automations and helpers, the template sensors and Jinja macros of the price, results, charge plan and climate, the two recorder scripts (battery full by sun end, indoor forecast), the energy, climate, results and home screens with their `cw-*` analysis topics, the dashboard builders and the design notes of cheap power, results, charge plan, the charger, the heat pump, climate and the dashboards. They contain personal data; see "Personal data in the sources" before porting anything.

`depends_on` may now name a **capability** (`tariff`, `ev-charger`, `heat-pump`, `hot-water-heater`): `tools/fill.py` accepts any chosen module whose `provides:` lists it and refuses two providers of the same capability. Templates see the chosen capabilities as `capabilities` (`<% if 'tariff' in capabilities %>`). `tools/choose.py` never adds a capability provider for you (brand and region are your choice): a module whose capability is missing is dropped with a note. Skeleton modules are not offered by `choose.py`.

### Decisions (and why)

1. **No separate `battery` module; `energy-plan` instead.** The only battery logic in the sources is a forecast (battery full by the moment the sun leaves the panels) plus "battery behind" with hysteresis. That forecast is "solar left today after the house"; it is just as useful without a battery (charge plan, hot water, appliances). The battery is an optional role inside `energy-plan`; the battery-behind sensor only exists with that role. The home battery in the source is not controllable, so there is nothing to actuate.
2. **`energy` is UI only; `energy-plan` is the logic layer.** The shared signals (export average, surplus on/off, house power, solar margin) were spread over helpers that charging, hot water, appliances and notifications all read. One owner without screens keeps the dependency graph flat: logic modules depend on `energy-plan`, never on the screens.
3. **Hot water split from the heat pump.** The boiler logic (surplus, cheapest hour before sunrise, shower and bath targets, price weighing) is brand-free once "heat to X °C" and "back to normal" are scripts. `heat-pump-vaillant` provides both `heat-pump` (floor) and `hot-water-heater` (tank); another brand provides the same scripts and sensors.
4. **Adapters provide normalised entities and scripts; cores never touch brand entities.** Same pattern for the charger (`script.ev_charger_set_mode`, `sensor.ev_charger_*`) and the heat pump (`script.heat_pump_set_floor_band`, `script.hot_water_heat`, `sensor.heat_pump_*`, `sensor.hot_water_temperature`). A second brand is a second adapter with the same ids.
5. **One writer per actuator.** The live setup has four writers of the charger mode, two of the car charge current and two of the hot-water boost, coordinating through text markers (with known races). In the kit: only `ev-charging`'s apply automation calls `script.ev_charger_set_mode`, only its car-amps automation writes `number.<car>_charge_current`, only `hot-water` calls the hot-water scripts, only `climate` calls the floor script. The markers become one `input_select.ev_charging_owner`. A screen that lets the user pick a charger mode (the energy screen) calls `script.ev_charging_manual_mode`, which only fires `ha_kit_ev_charging_manual`; the apply automation sets the owner to `manual` and calls the charger script. A direct call of `script.ev_charger_set_mode` from a screen would update the script's `last_triggered`, look like a call of the kit and be undone by the arbiter.
6. **Results is event-driven.** Producers fire `ha_kit_result` and `ha_kit_day_goal`; `results` only listens and sums. No producer depends on `results`, and `results` renders sensors only for the kinds of the installed modules.
7. **Capacity tariff lives in `tariff-be`**, including the 12-month average peak that was in the results templates: it is Flemish grid regulation, not a result.
8. **`climate` does not hard-depend on `shading`** (the README said it would): the shading block hides without it, and climate's own logic does not need shading helpers.
9. **`appliances-home-connect` stays one module** (adapter + logic): only one brand, and the logic is bound to Home Connect's program, remote-start and door entities. The seam for a later core is the start-window macro (solar window / cheapest quarter / deadline), kept in its own `custom_templates/appliances.jinja`.
10. **The Tesla command counter.** `counter.tesla_commands_today` stays owned by `gate`. Without `gate` in `modules:`, `ev-charging` defines the same counter in its own package (same id, same meaning). Adding `gate` later: fill in again and deploy `ev-charging` first (its definition disappears), then `gate`.

## 2. Shared rules for every phase-4 module

- **Notifications** go through `script.send_notification` (title, message, extra, optional `only_home: true` = only the recipients whose person entity is `home`; nobody home = nobody) when `'notifications' in modules`; without it, the module only writes the logbook. Only `appliances-home-connect` hard-depends on `notifications`.
- **Logbook**: `logbook.log` with `entity_id` = the module's master switch, texts through `t()`.
- **Fixed values are English** (states of template sensors, `input_select` options that automations compare, event data). Users see them translated by the screen or through `t()`.
- **No `initial`**: every tunable helper is in `defaults:` of its `module.yaml` (already listed in the skeletons; ids are part of the contract).
- **Recorder scripts** (`energy-plan`, `climate`) follow `presence`: Python in `/config/<module>/`, command_line in `/config/command_line/<module>.yaml`, read-only SQLite, entity and statistic ids passed as arguments (from `house.yaml`), never hard-coded; coordinates from `house.lat/lon`, time zone from `house.timezone`.
- **Frontend**: JavaScript in `/config/www/ha-kit/<module>/` (upload and register with `ha_api.publish_card(js, "ha-kit/<module>")`), custom elements with English names (`energy-screen-card`, `climate-screen-card`, `results-screen-card`, `home-screen-card`), entity ids come only from the card config that `fill.py` renders from `house.yaml` (no hard-coded ids, no serials, no names). Shared components stay `cw-*` from `base` (see CONTRIBUTING "Known naming leftovers"). UI texts in `strings.yaml`, passed into the card config as a `strings:` mapping.
- **A missing optional entity hides its block** (a chip without value is not drawn; a row without value says "no measurement yet"), never a bare "–" (design note of the climate page).
- **Units**: power in W unless the name ends in `_kw`; energy in kWh; prices in EUR/kWh; grid fees and levies in c€/kWh (as on Belgian tariff sheets). A role that may be W or kW is read with its `unit_of_measurement` (`energy-plan` has the macro `watts(entity_id)` in `custom_templates/energy_plan.jinja` for that).
- **Recorder statistics**: `energy-plan` reads the 5-minute statistics of the power roles and of `sensor.ev_charger_power`; every power sensor a module provides gets `state_class: measurement`.

## 4. Per module

Roles are `house.yaml` keys (see `house.example.yaml`); "(opt)" = optional.

### tariff-be (region)

- **Purpose**: Belgian (Flemish) dynamic tariff: price all-in per quarter hour from Nord Pool BE, day/night grid fees (Fluvius), levies, capacity tariff (quarter-hour peak, month peak, 12-month average, headroom), cheap window.
- **depends_on**: -. **provides**: `tariff`.
- **Provides**: the whole `tariff` contract above, plus helpers `input_number.tariff_grid_fee_day`, `tariff_grid_fee_night`, `tariff_levies` (c€/kWh), `tariff_capacity_eur_per_kw_year`, `tariff_fixed_eur_per_year` (EUR), `capacity_start_peak_kw` (fills missing months of the 12-month average), `capacity_margin_kw`, `power_price_cheap_below` (EUR/kWh); `input_boolean.capacity_peak_may_rise` (negative import price: headroom up to the connection limit `tariff.capacity.connection_kw`); automation `capacity_start_peak_from_meter` (copies the meter's average-peak register when `entities.grid_average_peak_kw` is set); `utility_meter` `sensor.tariff_grid_import_quarter` (15 min cycle) when the meter lacks the quarter register **or** the month-peak register (the computed month peak needs it too; one restart of HA after the first deploy). With a list in `entities.grid_import_kwh` it is fed by an extra template sensor `sensor.tariff_grid_import_total`. The average peak floors **every month** at `tariff.capacity.minimum_kw` (Flemish rule), not only the average.
- **Extras beyond the contract** (free to use, not required from another region): attribute `cost_eur_per_year` on `sensor.capacity_average_peak_kw`; macros `import_price()`, `export_price()`, `is_night()`, `kw()`, `quarter_energy()`, `rest_hours()`, `peaks_with()`, `average_peak()` in `tariff.jinja`; in `window.haKitTariff` an optional third argument `hass` on `importPrice` (uses the live grid-fee and levy helpers), `timeZone` and `VERSION`. `coefficients(hass)` is in the contract as an optional function (section 3; read by `results`).
- **Files in HA** (region-neutral, so a `tariff-nl` overwrites the same files): `/config/packages/tariff.yaml`, `/config/templates/tariff.yaml`, `/config/custom_templates/tariff.jinja`, `/config/www/ha-kit/tariff/tariff.js`.
- **Consumes**: `entities.spot_price` (any entity of the Nord Pool integration; the config entry is found with `config_entry_id()`, never written in a file), `tariff.area`, `tariff.import`, `tariff.export`, `tariff.night`, `tariff.grid`, `tariff.capacity` (with the optional `connection_kw`, default 9.2), `tariff.fixed_eur_per_year`, `tariff.cheap_below`, `entities.grid_import_w`, `entities.grid_import_kwh`, (opt) `entities.grid_month_peak_kw`, `grid_average_peak_kw`, `grid_quarter_kw`.
- **Port**: price template (trigger every 15 min + Nord Pool today/tomorrow) and its formula macros; month peak and expected-quarter sensors; the capacity average and `pieken_bij` macro from the results templates; headroom ("piekruimte") from the cheap-power templates; `cw-core.js` tariff helpers → `tariff.js`.
- **Personal data to strip**: Nord Pool config entry id; the household's own peak history and meter names; the formula coefficients come from `house.yaml`, never from code.

### energy-plan (core)

- **Purpose**: shared energy signals and the solar day plan: export average, surplus on/off, house power, when the sun leaves the panels, solar left today after the house and the battery, battery behind.
- **depends_on**: -.
- **Provides**: `sensor.energy_plan_export_avg` (kW, 10 min mean of `sensor.energy_plan_export_kw`, the export role normalised to kW), `binary_sensor.energy_plan_surplus` (a band around `input_number.energy_plan_surplus_kw`: on above threshold + `energy_plan_surplus_hysteresis_kw`, off below threshold − hysteresis, in between it keeps its state, like HA's threshold helper; off while the average has no value; attributes `export_avg_kw`, `on_above_kw`, `off_below_kw`), `sensor.energy_plan_house_power` (W; the role when set, else import − export + solar + battery discharge − charge; attributes `source` (`role`, `computed`) and, with `ev-charger`, `without_car` (W)), `sensor.energy_plan_margin` (kWh; attributes `after_sun` (bool), `sun_end` (ISO), `sunset`, `battery_needed_kwh`, `pv_remaining_kwh`, `pv_remaining_forecast_kwh`, `pv_remaining_history_kwh`, `house_remaining_kwh`, `source` (`forecast`, `history`, or null after the sun); `sun_end` and `sunset` are ISO with minutes and offset; extra attributes `sun_end_offset_min`, `battery` (bool), `forecast_factor`, `pv_today_kwh`, `days`, `error` (null, a reason, or `warning: …`); always numeric, `unavailable` when the script fails), `binary_sensor.energy_plan_battery_behind` (only with `battery_soc`; on when margin < `input_number.energy_plan_battery_safety_kwh` and the sun is still on the panels, never at SoC ≥ 98 %, off only above safety + `energy_plan_battery_hysteresis_kwh`; attributes `margin_kwh`, `sun_end`, `on_below_kwh`, `off_above_kwh`). Script `/config/energy-plan/energy_plan.py`. Macro `watts(entity_id)` in `custom_templates/energy_plan.jinja` (a power role in W by its unit), usable by other modules.
- **Consumes**: `entities.grid_import_w`, `grid_export_w`, `solar_power_w` (required: no plan without PV), (opt) `battery_soc`, `battery_power_w` + `energy.battery_power_sign`, `energy.battery_usable_kwh`, `house_power_w`, `solar_forecast_remaining_today`, `solar_forecast_today`, `solar_forecast_updated` (timestamp of the last forecast refresh; corrects the hourly saw-tooth; empty = the moment `solar_forecast_remaining_today` last changed), `charger` power for "house without the car" (`sensor.ev_charger_power` when `'ev-charger' in capabilities`; its 5-minute statistics, without them the car counts as house load and `error` has a warning); `house.lat/lon/timezone`; (opt) `energy_plan.sun_end_w`, `charge_efficiency`, `history_days`. The power roles need `state_class: measurement` (5-minute statistics); the recorder must be SQLite.
- **Port**: battery-full script (parameterise ids, coordinates, usable kWh, PV threshold), the battery-behind template with hysteresis helpers, the statistics/threshold helpers "export average 10 min" and "surplus available" (UI entries become YAML in the package).
- **Strip**: coordinates and device names in the script; battery brand device name.

  - Provides also `input_number.appliances_solar_minimum_kwh` (default 10 kWh: wait for sun only from this expected solar) and `input_datetime.appliances_solar_peak` (time, default 15:00: the safety net of a plan that waits for sun is the program centred on it), both only with `energy-plan`; `input_number.appliances_battery_minimum` exists only with `energy-plan` and `entities.battery_soc` + `solar_power_w`; internal `script.appliance_notify` (to who is home, everyone when nobody is). `appliance_start_now` `start_in` is "start in" for dishwashers and becomes "finish in" = `start_in` + duration for washers and dryers (`appliances[].delay_option`).
  - Consumes also `entities.solar_power_w`, `entities.solar_forecast_tomorrow`, `binary_sensor.energy_plan_battery_behind` (the battery start waits while the battery is behind), `sensor.energy_plan_margin` attributes `after_sun` and `pv_remaining_kwh` (today's sun without a forecast role), `house.yaml home_connect:` (`language`, `entities`); `appliances[]` also `name`, `auto_time`, `delay_option`, `entities`, `maintenance`.
  - Logbook: the module has no master switch; its logbook lines use `input_boolean.appliance_<key>_smart_waiting` as entity.
  - Order of priorities of the start window: sun or battery > deadline > price. The safety net while waiting for sun is the sunniest moment, not the cheapest quarter (with a battery the surplus comes late in the afternoon).
  - Needs Home Assistant 2026.4 or newer (`home_connect.start_selected_program`).
  - Not fired: `ha_kit_result` kinds `appliance_solar` / `appliance_cheap` (they need an energy estimate per program; open point in section 8).
- **Strip**: Home Connect device ids, person routing by name.

### results (core)

- **Purpose**: what the smart logic saved and whether the day goals were met; consumption and cost per day, week and month against the invoice; last year; what the house did (logbook).
- **depends_on**: `tariff`. Optional: `energy-plan`, `hot-water`, `ev-charging`, `shading`.
- **Provides**: `sensor.results_saving_<kind>` (EUR, `state_class: total`; attributes `kwh`, `export_missed`, `actions`) for the kinds of installed producers (`hot_water_solar`, `hot_water_cheap_hour`, `ev_solar`); `sensor.results_shading_closed_count`; `sensor.results_solar_missed_today` (kWh exported while the tank or a connected car still had room); `sensor.results_goal_<goal>` (`met`, `missed`; attributes `date`, `detail`) for `morning`, `bath` (hot-water) and `solar_used` (23:55); `sensor.results_invoices` (attribute `invoices`: `[[YYYY-MM, EUR], …]`) with `input_number.results_invoice_last_month`; card `custom:results-screen-card`.
- **Events consumed**: `ha_kit_result` `{kind, kwh, eur, export_missed}`, `ha_kit_day_goal` `{goal, status, detail}`; `ev_solar` is computed from `sensor.ev_charger_solar_energy_today` × `sensor.power_price_import`.
- **Consumes**: `tariff` (prices, `sensor.capacity_average_peak_kw`, fixed costs and capacity helpers), `entities.grid_import_kwh`, `grid_export_kwh`, cost sensors of the HA energy dashboard (`results.cost_sensors`, opt), battery and PV energy roles, `results.last_year` (opt, local only), `results.exact_from`.
- **Port**: results templates (savings, counters, goals, invoices), the tracking automation (split: producers fire, results listens), results screen.
- **Strip**: the real last-year settlement (kWh and EUR per month) and invoice totals: they become `house.yaml results.last_year` (local), never code.
- **Notes from wave 1**: `sensor.capacity_average_peak_kw` has the extra attribute `cost_eur_per_year`; `tariff.jinja` has `peaks_with()` and `average_peak()` (what a peak would do to the average). `sensor.ev_charger_solar_energy_today` exists only when the charger has a green-energy register (Zappi: `charger_solar_energy_today` or the prefix): hide `ev_solar` without it.
- **Built (wave 3)**:
  - Provides also `sensor.results_saving_ev_cheap`, `_appliance_solar`, `_appliance_cheap`, `_peak_avoided` (extension kinds, rendered with their producer, shown on the screen only after a first event); attributes of every saving sensor `kwh`, `export_missed`, `actions` (+ `last`; `ev_solar` also `kwh_unpriced`, `counter`, `day`; `peak_avoided` also `kw`); `sensor.results_solar_missed_today` attributes `day`, `export_total`, `exported_today`, `room`; `sensor.results_shading_closed_count` attribute `last_room`; helpers `input_number.results_solar_missed_max_kwh` (1 kWh), `results_compare_variable`, `results_compare_fixed`, `results_compare_export` (c€/kWh, start values from `tariff.compare`, 0 = not compared); automations `results_solar_used_goal`, `results_log_saving`; macros `custom_templates/results.jinja` (`counter_step`, `export_total`, `room_now`); view path `results.view_path` (default `results`), extra logbook entities `results.log_entities`.
  - `ha_kit_day_goal` `goal: solar_used` is fired by results itself at 23:55. A correction `ha_kit_result {kind: ev_solar}` (e.g. a day before the tracking) is added to the computed `ev_solar`.
  - Consumes `window.haKitTariff.coefficients(hass)` (optional part of the `tariff` contract, section 3) for the comparison with other contracts; without it that block hides. Also `sensor.capacity_month_peak_kw`, `input_number.tariff_capacity_eur_per_kw_year`, `capacity_start_peak_kw`, `tariff_fixed_eur_per_year`; `sensor.ev_charger_connected` / `_status` / `_power`; `input_boolean.hot_water_on_surplus`, `input_number.hot_water_surplus_max`, `_minimum`, `_shower`, `_bath`, `input_datetime.hot_water_bath_check`, `sensor.hot_water_temperature`; `sensor.ev_charging_energy_needed`; `input_boolean.shading_closed_<room>`.

### home-screen (core, UI)

- **Purpose**: start dashboard with one chip or card per installed module, an advice line (price), energy in four tiles, quick toggles, the arrival card of the cars.
- **depends_on**: -.
- **Provides**: a view `home` (path from `home_screen.view_path`) with `custom:home-screen-card` (`/local/ha-kit/home-screen/home-screen.js`) on a dashboard of your choice: default the Overview, `deploy.py --dashboard <url_path>` for another one (created when missing). Not a dashboard `home`: a dashboard url_path needs a hyphen in Home Assistant.
- **Card config** (rendered from `modules`, `capabilities` and `house.yaml`): `features:` one boolean per block, derived only from `modules:`/`capabilities` (`climate`, `gate`, `shading`, `presence`, `cars` (`tesla-route`), `doorbell`, `parcel_service`, `ev_charging`, `tariff`, `energy` (`energy-plan`), `hot_water`, `cameras`, `media`, `todo`); `roles:` the entity ids it shows; `cars:`, `people:`, `rooms:` lists from `house.yaml`; `toggles:` (`home_screen.toggles`), `media_players:`, `cameras:` (pattern), `paths:`; `map:` (optional Mapbox token from `home_screen.map_token`, local only); also `capacity_minimum_kw` (`tariff.capacity.minimum_kw`), `comfort` (`climate.comfort`) and `protect_url` (`home_screen.protect_url`). The card reads every power role with its `unit_of_measurement` (W or kW).
- **Same optional reader**: `e-ink-display` (not a phase-4 module) reads `sensor.power_price_import` (`starts`, `prices`, `cheapest_2h`), `sensor.energy_plan_house_power`, `sensor.energy_plan_margin` (`pv_today_kwh`) and `sensor.hot_water_temperature` the way `home-screen` does, without `depends_on`: keep them.
- **Reads from other modules** (each only with that module in `modules:`): see the rows that name `home-screen` in "Contracts between modules" (README). `ev-charging` must keep `input_boolean.ev_charging_smart` and attribute `target_percent` of `sensor.ev_plan_<prefix>`; `energy-plan` keeps `binary_sensor.energy_plan_surplus` and `sensor.energy_plan_house_power` in W.
- **Deploy**: `deploy.py --dry-run --live` reads the dashboard and the resources (read-only) and prints the real diff; see CONTRIBUTING "deploy.py".
- **Port**: home screen without the presence card (that stays in `presence`).
- **Strip**: names of people, children and cars; the work zones; a street in a comment; the home-location fallback coordinates; the UniFi console IP; the Mapbox token; light and plug names.

Wave 1 (no phase-4 dependencies, start together): `tariff-be`, `energy-plan`, `charger-zappi`, `heat-pump-vaillant`, `home-screen` (render from flags; real data later). **Built and integrated** (not tested on HA).

After adding `ev-charging`, fill in again and deploy `notifications` (it leaves out a notification then).

Every builder can start in wave 1 against the contracts above (entity ids are fixed here); later waves only need real entities for the HA test plan.

**Rules for builders (no collisions):**

1. Write only in your own `modules/<name>/`. Do not edit `house.example.yaml`, `README.md`, `CONTRIBUTING.md`, `tools/`, `tests/` or another module.
2. Need a new `house.yaml` field? Put it in `modules/<name>/house.fragment.yaml` (never copied). Need a change outside your folder (another module, a tool, the README)? Write it in `modules/<name>/HOUSE-CHANGES.md`. The integrator merges both.
3. Keep the entity ids, helper ids, event names and states of this document. A change to a contract is a change to this file first (ask the integrator).
4. Optional switches that need both branches tested: add `check_variant:` to your `module.yaml` (`{section: {key: value}}`), not to `tools/check.py`.
5. When you replace a skeleton: set `status:` to `built, not tested on HA`, add `deploy.py` (with `--dry-run`) and keep `tools/check.py` passing. `choose.py` starts offering the module as soon as its status no longer starts with `skeleton`; add the answer for its question to `tests/choose.answers.yaml` and `tests/choose.no-brands.answers.yaml` and the module to `EXPECTED_CHOICE` (and, when it needs no missing capability, `EXPECTED_CHOICE_NO_BRANDS`) in `tools/check.py`.
6. No personal data: see below; run `tools/scan.py` (with the denylist) before every commit.
